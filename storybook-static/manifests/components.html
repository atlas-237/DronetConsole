# Catalogue des stories

Cette page décrit le périmètre couvert par Storybook pour DronetConsole. Chaque story est un scénario de référence : elle montre un état visible, les propriétés importantes à contrôler et, lorsque c'est pertinent, le comportement attendu après une interaction.

## Lire une story

- **Default / Standard** : état nominal à utiliser comme point de départ.
- **Variant métier** : combinaison de données représentative d'une opération réelle.
- **État limite** : vide, erreur, chargement, danger, désactivé ou contenu volumineux.
- **Interaction** : scénario pilotable avec les contrôles Storybook ou les boutons de la story.
- **Responsive** : story prévue pour être vérifiée avec les viewports desktop et mobile.

Les composants partagent le thème Darta chargé par `.storybook/preview.ts` et `src/theme/index.css`. Les couleurs, espacements et polices utilisent les tokens du thème ; les composants migrés utilisent les utilitaires Tailwind v4.

## Source de vérité

Le catalogue Storybook actuel est composé de **70 stories colocalisées** dans `src/components/**`. Chaque composant documenté doit conserver son fichier `Component.stories.tsx`, activer `autodocs` et fournir `parameters.docs.description.component`.

Les anciens catalogues sous `src/stories/**` ne font plus partie de l'arborescence active. Les exemples de cette page qui décrivent encore ces anciens regroupements sont des scénarios fonctionnels historiques ; la story colocalisée du composant est la référence à ouvrir dans Storybook.

## Règles de maintenance

Lorsqu'un composant reçoit une nouvelle prop ou un nouvel état visuel :

1. Ajouter ou modifier un `argType` avec une description et une valeur par défaut.
2. Ajouter une story nommée qui montre le comportement concerné.
3. Documenter l'interaction attendue dans la description de la story.
4. Ajouter un test pour la prop critique ou le callback associé.
5. Vérifier `npx tsc --noEmit` et `npm run lint` avant de publier la documentation. Les builds sont exécutés séparément dans la CI ou lors d'une validation de release.

Les stories servent de contrat visuel et comportemental ; elles ne doivent pas dépendre d'une API distante ni de données aléatoires non contrôlées.
